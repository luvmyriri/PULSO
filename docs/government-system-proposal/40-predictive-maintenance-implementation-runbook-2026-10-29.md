# Predictive maintenance implementation and release runbook

**Status:** Implemented in repository; production model release and citywide service acceptance remain pending. **Date:** 29 October 2026. This supplements the proposed [release plan](39-production-predictive-maintenance-release-plan-2026-10-29.md). The code implements an outcome-based path without activating an unvalidated model. It does not turn the proposed LGU policy into an approved decision.

## Implemented contract

- Additive Alembic revision `20d4e5f6a7b8` adds candidate/verified asset registry state, maintenance authority/source, private inspection evidence, independently reviewed inspection outcomes, persisted assessments, and scoring-run history. Revision `21e5f6a7b8c9` adds sourced weather and river forecast snapshots. Existing asset, report, work-order, and legacy predictive endpoints remain present.
- Engineering leaders verify a sourced asset and field location. Qualified inspectors record a no-defect or defect finding; defect findings require a private image. An authorized independent reviewer verifies or rejects it. Submitted findings do not change condition or train a model. Evidence is stored outside the public uploads mount and served only through staff and asset-scope checks. The worker purges private images left unattached to any inspection after 24 hours.
- Offline training uses verified no-defect baselines and later verified defect or no-defect follow-up. Unobserved windows are censored. Forward training, calibration, and holdout periods are separate. A release is refused unless the owner-supplied policy and holdout gates pass. The serving API loads an immutable, SHA-256 checked artifact; it never trains in a request.
- A scheduled worker scores only the approved class and barangays. A verified baseline must be at most seven days old. Status, ranked queue, asset assessment, and CSV fail closed if the artifact or run is absent/stale. The existing rules/recorded-condition workflow stays available, with production probability shown separately.
- The model output is the chance of a **new verified actionable defect within 90 days of the verified baseline**. It is not a rolling 90-day forecast, a flood prediction, an asset failure-time estimate, or a work authorization. CSV includes the baseline, window end, assessment time, and model digest.

## Release procedure for the named cohort

1. Record the City Engineer's cohort, maintenance authority, label definition, inspection rubric, capacity, threshold values, data steward, privacy/records owner, security owner, and a dated go/no-go decision. Confirm the real registry and inspection totals; do not infer them from local or dated VPS screenshots.
2. Back up the production database, `private_publications`, and current predictive artifact directory. Rehearse restore on an isolated instance. Confirm `scripts/db_schema.py check-existing` reports the expected pre-upgrade revision and no schema drift. Migrate with `alembic upgrade head`; then run `scripts/db_schema.py assert-revision 21e5f6a7b8c9` and `check-existing` again. Do not run the disposable database test script against the application database.
3. Verify official asset records through the scoped registry action. Collect both positive and negative field observations, independent reviews, and work/maintenance history. Run `python backend/scripts/inspect_production_predictive_readiness.py --category <approved-class> --barangay-id <id>` with `DATABASE_URL` set. It reports counts, not citizen or staff data. A missing forward split or too few verified outcomes blocks model publication.
4. Write a restricted policy JSON with: `approved_by`, `approval_reference`, `approved_barangay_ids`, `inspection_capacity`, `minimum_hazard_coverage`, `minimum_train_events`, `minimum_calibration_events`, `minimum_holdout_events`, `minimum_top_k_precision`, `minimum_lift_over_condition_baseline`, `minimum_hazard_incremental_precision`, `maximum_brier`, `minimum_critical_holdout_events`, and `maximum_critical_miss_rate`. Thresholds must be set **before** reviewing the final holdout. Training is invoked offline with `python backend/scripts/train_production_predictive.py --category <approved-class> --policy <restricted-policy.json> --output <new-immutable-release-dir>`. It refuses insufficient data, failed metrics, and existing output directories.
5. Review the generated manifest, feature/label lineage, subgroup metrics, critical misses, and checksum with the named owners. Benchmark scoring and memory on production-like data. Place the approved immutable release in `/opt/pulso/shared/predictive/<release-id>` and point `/opt/pulso/shared/predictive/current` to it in a controlled release. Confirm file permissions, database migration, and deployed image revision. Restart API and worker to load the new artifact; run one scoring cycle and inspect `/api/gov/predictive/production/status` with an authorized staff session.
6. Verify scope, private evidence access, audit history, CSV content, failure/stale behavior, responsive and keyboard use, and the separation of report/work-order decisions. Record signed acceptance and support/on-call ownership. Keep the previous artifact and database backup for rollback. To suspend the model, remove or repoint `current`, restart API/worker, and confirm the UI displays model unavailable while recorded maintenance reviews still work. Issued work orders continue under their normal workflow.

## Current release blockers and limits

- **Local development check, 29 October 2026:** a backup was saved before applying revision 20 to local `pulso_db`. The local database has 34 asset records, zero verified assets and zero reviewed observations, so Drainage has zero labeled training windows. The schema inventory checker also reports pre-existing differences in `agent_locations`, `chat_conversations`, `reports`, `system_documents`, and `work_orders`; these must be reconciled before that database can serve as a production-like schema acceptance result. This is a local observation, not a VPS audit.
- No authentic historical cohort, label audit, approved threshold policy, model artifact, or live VPS validation has been supplied in this repository task. The new endpoint must report `unavailable` until these are real. No calibrated production percentage or citywide prediction can be claimed yet.
- External PAGASA/GeoRisk/utility feeds and a reconciled citywide asset inventory are not integrated here. Existing location/map and recorded-condition functions remain; hazard exposure cannot be described as a validated model feature.
- The inspection ledger is asset-centered. Assignment of a dedicated inspection task into My Work, inspection rubric/versioning, corrections/supersession, intervention completeness checks, confidence intervals, and incident alert delivery still need named operational contracts and implementation before the broader plan's P3/P4 acceptance can be signed.
- This repository implementation reused the current visual system. The required Figma reconciliation, responsive accessibility review, production-like load run, backup/restore rehearsal, and authorized role walkthrough have not been completed. Do not treat a passing local build or disposable database test as a deployment approval.
