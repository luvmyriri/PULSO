## Direction

Carry the Reports header, restrained filters, quiet ruled rows, selected-record marker and evidence-led detail into the workspaces where each pattern serves the task. Use soft neumorphic depth at points of interaction. Give actionable buttons a shallow lift, editable fields a slight recess and pressed controls a short change in depth. Keep rows and case facts on quiet surfaces. Let the evidence or map carry the visual emphasis, with real source, time and location metadata in its rail. Use the same control and feedback styles in dashboards, stand-alone forms and staff access screens while retaining their task-specific layouts.

Light mode uses white work surfaces, dark-blue text and crisp rules. Dark mode uses deep survey blue and tonal separation. Use the Reports typography and geometry as rendered. The approved October 27 roles assign orange to primary emphasis and pale green to selections. The government surface CSS already gives primary buttons an orange fill, while some selected controls and report rows use warm orange. Older guidance assigns Field Blue to primary actions. Verify which declarations win in each component and scope the pale-green correction to selection. Preserve distinct severity, resolved, warning, critical and focus roles. [Product commitments](../../PRODUCT.md) · [Civic Aperture v0.2](09-visual-art-direction-v2.md) · [Government surface overrides](../../frontend/src/styles/government-surfaces.css#L28)

Extend the tactile rules already used by `.gov-experience`, including the shared `--workspace-control`, `--workspace-inset` and `--workspace-raised` recipes. `GovWorkspace` exports controls, tables, detail panels and confirmations. Its `GovState` shows a generic loading line, while Reports adds its own status text and refresh spinner. `useGovernmentData` keeps same-path data during refresh and exposes loading, error and fetch time. Reports has a separate queue request path. Apply one visual state contract across both paths and account for differences in cancellation, scope and receipt behavior. ## Shared component work

| Family | Treatment | Behavior and states |
| --- | --- | --- |
| Buttons and icon actions | Shallow raised surface for standard actions. Orange primary treatment for the main decision. Neutral secondary and quiet text actions. Use a distinct semantic danger treatment for destructive actions. | Define default, hover, focus, pressed, selected, disabled and busy states. Keep the label and button width stable during submission. Use an action label such as “Assign reviewer,” then “Assigning…”. Guard repeat submission and show the resulting receipt or error. Icon-only actions need an accessible name and a visible label where the action would otherwise be ambiguous. |
| Forms and filters | Slight inset on text fields, search and text areas. Defined borders, persistent labels and readable hints. Keep one column on narrow screens and use two only for naturally related fields. | Specify empty, populated, focus, invalid, disabled, read-only and saving behavior. Associate errors with fields and focus the first invalid control or the error summary on submission. Placeholders may show an example value. Put instructions and required information in labels and hints. Preserve safe input through validation, upload failures and conflicts. |
| Selects, toggles and tabs | Reuse the shared control geometry. Use pale green plus a check, marker or text cue for selection. | Keep keyboard behavior and selected state exposed to assistive technology. Scope the busy cue to the result region while filters remain usable. Keep approved navigation defaults and backend capability checks in place. |
| Tables, queues and dockets | Flat ruled rows, a restrained selection marker and one contained docket. Apply soft elevation to the panel boundary where it helps separate work. | Preserve column semantics, filter and sort state, selected record, pagination, freshness and back navigation. Return focus to the source row or a stable queue control when a record moves out of scope. |
| Dialogs, drawers and upload controls | Opaque surface, shallow separation and a clear action footer. Use a compact receipt and progress region near the action. | Preserve consequences, reason and confirmation for governed decisions. Set initial focus, support Escape where cancellation is safe, and restore focus on close. Distinguish uploading, upload complete, saving, committed, failed and uncertain receipt. Show percentages only when progress is measurable. |
| Maps, evidence and charts | Preserve true-color evidence. Use reserved aspect ratios for evidence and map regions. Use the existing subtle raised chart bars and recessed tracks. | Keep address and list alternatives for maps and exact values and summaries for charts. Provider failure leaves the text or data alternative available. An unverified location, missing photo, unavailable chart and genuine zero each have separate copy. |

Use existing semantic variables for canvas, surface, text, control boundary, action, selection, focus and status. Keep the depth scale small with flat, shallow raised, inset and overlay roles. Scope the recipes to the government shell and its portalled dialogs. Inventory consumer styles before replacing shared declarations. Use real borders and state cues so the controls remain legible when shadows disappear in forced colors. The project calls for a visible 3 px focus ring. Test essential control boundaries and state indicators at 3:1 against adjacent colors. [W3C non-text contrast](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)

## Loading and recovery

Use a shared presentation contract for route startup, a loading region and an action in progress. Reuse `GovState` and the request state where practical. Add variants for the shape of the content and derive state from request, authorization and receipt evidence. Keep authorization pending distinct from data loading. The shell can show a neutral structure while permissions are checked. Show scoped labels, navigation and data after authorization resolves.

| State | What staff sees and can do |
| --- | --- |
| First load | Render the authorized shell and a region-sized placeholder. Use “Loading report queue…” or another task-specific label. Keep the page title, toolbar and region geometry stable while data arrives. |
| Fast response | Render data as soon as it is ready. Pilot a roughly 150 ms delay before showing the visual skeleton to avoid flashes. Apply no minimum display time. |
| Slow response | Keep the region visible with a plain status message. Pilot a “Still loading” message around 8 seconds and provide cancel or retry where the request supports it. Recheck those thresholds against observed pilot latency. |
| Refresh of the same result set | Keep authorized rows and the selected record visible. Mark the region “Refreshing…” and show its last successful update. Keep pagination, filters and scroll position stable. |
| New search, sort, page or selected record | Keep the shell and relevant controls stable while the affected region loads. Associate rows, totals, timestamps and action targets with the result that produced them. Keep the selected docket only if it remains in the authorized scope. Cancel or ignore late responses to older queries. Clear previous scoped data on account, jurisdiction or capability changes. |
| Partial data | Show successful regions. If the report loads and the photo or map fails, show a local retry and the relevant text alternative. Keep any action that depends on missing evidence unavailable with a reason. |
| Empty or filtered out | Show “No reports in this queue” after a successful empty response. For active filters, show “No reports match these filters” and offer to clear them. |
| Offline, stale or failed | Keep still-authorized same-scope data with a last-updated label and a clear recovery action. Show a recoverable error for a failed first load. Keep edits or drafts only where the existing storage and permission rules allow it. |
| Denied or session expired | Show a permission state or a sign-in action with a safe return path. Conceal scoped records and actions while access is unavailable. |
| Saving, conflict or uncertain result | Show local progress and preserve safe input. On conflict, reload the record and ask the employee to review it again. On a lost response, recover the original receipt when that command supports recovery. Announce success after the server confirms the result. |

Design skeletons as shapes that reserve space. A queue uses its real table header and a few neutral rows. A docket reserves the heading, evidence frame and fact rows. A form keeps real labels when known and reserves the field slots. A dashboard reserves the chart footprint with a neutral panel and loading label. A map reserves its canvas and address/list area. Skeletons carry no fake values, pins, statuses or interactive controls. Hide decorative shapes from assistive technology and announce the meaningful state once per region. Use static skeletons and a scoped progress indicator when it helps the task. [W3C status messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)

## Motion budget

| Trigger | Proposed treatment |
| --- | --- |
| Hover, press and field state | Roughly 100–150 ms for a control's tone or depth. The focus ring appears immediately. Keep hit targets and layout stable. |
| Queue selection and detail update | One 160–180 ms transition when the selection actually changes. Keep the queue and its scroll position stable. Preserve the evidence frame as the new record arrives. |
| Dialog, drawer and disclosure | Use a short fade for the dialog and the existing approximately 220 ms drawer travel as the starting point. Apply focus and keyboard behavior independently of motion. |
| Confirmed lifecycle event | Use the existing Signal Cut once for an actual transition, paired with the recorded label and time. Preserve the dossier's 320–450 ms working range. |
| Reduced motion and forced colors | Present the final state immediately under reduced motion. In forced colors use system foreground, boundary, selection and focus cues. |

Animate only changes that help staff follow an action. Prefer opacity and transforms for overlays and avoid layout-wide animation on queues, maps and tables. Keep evidence pixels and form text still while staff inspect or edit them. [Civic Aperture motion guidance](09-visual-art-direction-v2.md)

## Browser verification and repository handoff

- Check both themes at 1280×720, tablet and 320 CSS px, plus native browser zoom at 200%. Verify labels, dialog scrolling and action visibility. Keep horizontal scrolling inside labelled table or map regions where a two-dimensional layout is necessary. [W3C reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)
- Run keyboard and screen-reader checks for selection, field errors, modal focus, busy announcements, errors and completion. Test forced colors and reduced motion. Exercise long labels and Filipino expansion where shared copy appears. Keep resident-facing localization as a separate existing contract.
- Check screen-reader table headers at narrow widths, custom filter keyboard behavior, and portal overlays outside the core workspace. Exercise rapid query and selection changes during polling, and verify that access revocation and account switches clear stale sensitive data. [Shared responsive table CSS](../../frontend/src/components/government/gov-workspace.css#L149) · [Reports filter control](../../frontend/src/components/OrangeSelect.jsx)
- Compare controlled fast, slow, offline, partial and denied scenarios against the Wave 0 baseline. Check for layout jumps at queue, evidence and form swaps. Confirm motion does not defer data or focus. Capture any regression with the request state, viewport and theme so it can be reproduced. Use synthetic evidence for test captures.
- Review changes in a local browser against the captured Reports baseline. Attach before/after captures in both themes to the implementation review with route, viewport, test role, data state, and any deliberate deviation. Keep the reusable component, token, state and acceptance notes with the code review. Capture sensitive workflows using synthetic records.

This planning phase delivers the route sequence, component contract and review gates. The first implementation slice is the paired Reports pilot with its shared primitives. Timing values and rollout order are proposed defaults for that pilot.
