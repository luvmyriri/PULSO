# Government assistant: Gemini and recorded operational evidence

Status: observed implementation, explicitly requested by the user. Version 2.0,
validated 28 October 2026. Owner: PULSO product/LGU decision owners. This replaces
the OpenAI-only/no-records contract in document 35. It does not approve a production
privacy policy or validate a predictive model for engineering decisions.

## User outcome and interface

Government staff can summarize authorized workload, inspect a referenced report or
work order, and review registered infrastructure using recorded condition,
maintenance history, PostGIS proximity and available experimental LightGBM results.
The existing vertical dashboard conversation and floating launcher on other pages
remain. The outdated OpenAI/About popup is removed. The footer names Gemini.
Each answer can display its server-generated source links, scope and query time.
Experimental model use carries a short engineering-review limitation.

No resident UI or resident assistant behavior is changed. Existing tokens,
typography, light/dark styling, scroll behavior, keyboard support and composer
geometry are retained. Source disclosure uses native details/summary, wrapping
links, 44 px targets and 3 px focus. No Figma mutation or live visual validation is
claimed; this is a functional integration within the incumbent assistant surface.

## API and authorization

`GET /api/gov/assistant/status` reports Gemini configuration, respecting the server
kill switch and staff assistant permission. Configuration is not a provider-health
guarantee. `POST /api/gov/assistant/messages` retains bounded, alternating recent
conversation and a page label, with optional `report_id`, `work_order_id` and
`asset_id` references. References never grant access.

Fixed server queries build evidence before calling Gemini. There is no model SQL,
arbitrary query tool, web access or mutation capability. Reports, work orders and
assets honor module grants and configured district scope. Field employees receive
their own assigned work and linked reports. Explicit denials exclude that module.
Referenced out-of-scope records contribute no detail. Records/admin data are not
added to this adapter. Resident identities, contacts, exact coordinates, evidence,
descriptions and confidential notes are excluded from automatic grounding.

The adapter supplies current workload/status aggregates and up to three referenced
reports. Maintenance inquiries use at most three requested assets, or the three
lowest recorded condition scores, explicitly labeled as a condition-based subset.
It does not claim a citywide model ranking. Source links are generated by the
server; unknown model-returned source IDs are rejected. Previous assistant messages
and all data strings remain untrusted, subordinate to system instructions.

## PostGIS, history and model truth

The existing scoped asset map context supplies actual `ST_DWithin` proximity
counts within 500 m during 90 days, separately from explicit report/work links.
Missing geometry produces an unavailable count, never zero. Dated maintenance
projections reuse the existing median-interval method, requiring at least three
distinct completions of the same work type. They are planning prompts.

The existing LightGBM engine combines synthetic training examples and registry
proxy labels. The assistant exposes its output as an **experimental review index**,
never a validated failure percentage, promised repair duration or approved schedule.
It does not expose the current model's default repair quantiles as factual deadlines.
Inference requires registered geometry and recorded condition. Model failures leave
record/history evidence available, with an unavailable model state. The existing
citywide model is withheld for district-restricted accounts and narrower data grants;
no hidden citywide training results cross those boundaries.

## Provider and failure behavior

The government adapter reuses the resident integration's configured Gemini client,
model and daily/per-user/burst budget protection. Credentials remain server-only;
either configured Vertex service-account access or the existing Gemini key pathway
works. The [Google Gen AI SDK](https://googleapis.github.io/python-genai/) provides
generation configuration and typed JSON output. No new credential is needed in a
checkout whose resident Gemini integration already works.

Questions and the minimal operational evidence above are processed by Gemini.
Application chat remains in component memory and clears on reload/sign-out; this
does not imply zero Google retention. Production processing/retention approval is
still the LGU privacy owner's responsibility. Model assistance remains advisory.

Database failure is a recoverable error, never a successful zero/empty answer.
Provider denial, quota, timeout, invalid output and unverifiable source IDs return
sanitized errors with the question retained for edit/retry. Staff-account rate
limits and shared Gemini budget/kill-switch controls remain enforced. No assignment,
approval, publication, email or other civic record mutation is performed.

## Validation

- 29 automated router/grounding checks cover authentication, explicit denials,
  district/field restrictions, private-field exclusion, real PostGIS counts,
  actual LightGBM inference, missing inputs, budget limits and provider failures.
- A live Gemini call successfully used the local application database: 10 open
  reports and 2 current work orders, with matching authorized source IDs.
- Read-only live asset check for `CAL-DR-176B` returned recorded condition 27/100,
  zero nearby reports within the defined 90-day/500 m window, and an experimental
  LightGBM review index of 78.6. These are dated local application records, not
  independently verified city data or a validated failure probability.
- Frontend production build and targeted ESLint passed. Existing bundle-size
  warnings remain. The running backend exposes the updated request schema and the
  development frontend serves the changed component.
- Live visual, keyboard, 320 px/200% zoom and theme inspection remain unverified
  because local browser control is disabled in Work settings. Shared Figma is
  unchanged; its assistant annotations should be reconciled when editing is available.
