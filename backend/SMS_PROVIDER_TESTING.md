# SMS provider integration testing

Set `SMS_PROVIDER=semaphore`, `SMS_PROVIDER=philsms`, `SMS_PROVIDER=iprogsms`, or `SMS_PROVIDER=textbee` in the ignored local file. Semaphore uses its OTP route for resident phone sign-in and its priority route for staff alerts. PhilSMS requests its documented plain SMS route for both, but outbound PhilSMS is disabled by default because the live pilot was classified as Voice. IPROG SMS uses a caller-generated OTP in its single-message route and is disabled by default until a handset test passes. TextBee dispatches SMS through a paired Android gateway device via `https://api.textbee.dev/api/v1/gateway` (`x-api-key` header) when `TEXTBEE_ENABLE_OUTBOUND=true`. Missing credentials, HTTP errors, malformed responses, and failed statuses return failure. The code never prints OTPs or API credentials. A provider accepting a request does not prove handset delivery.

## Local setup

1. Rotate the API key previously shared in chat. Put the replacement in the ignored `backend/.env.local` as `SEMAPHORE_API_KEY=...`. The repository already tracks `backend/.env`, so never put a new secret there. Do not commit or paste the replacement into messages.
2. If your Semaphore account has no active default sender name, add an approved `SEMAPHORE_SENDER_NAME=...` in the same local file. Do not assume `PULSOLGU` has been approved.
3. Set a strong `JWT_SECRET_KEY` in `backend/.env`; phone OTP endpoints refuse to operate without it.
4. Keep `PULSO_ENABLE_PRIORITY_SMS=false` while testing OTP. Set it to `true` only after the LGU approves automatic priority alerts and the intended recipients.
5. Restart the backend after changing local environment files so the running process reads the new values.

For PhilSMS, set `SMS_PROVIDER=philsms`, `PHILSMS_API_TOKEN=...`, and an account-approved `PHILSMS_SENDER_ID=...`. Leave `PHILSMS_ENABLE_OUTBOUND=false` while the channel discrepancy is unresolved. Its [current account documentation](https://dashboard.philsms.com/developers/docs) requires a sender ID and describes `type=plain` for SMS. The phone number is normalized to `639...` before dispatch. The account token provided for this pilot authenticated against `dashboard.philsms.com/api/v3` and was rejected by the older `app.philsms.com/api/v3` host, so this adapter uses the dashboard host. The dashboard warns that the default `PhilSMS` sender ID works for Globe subscribers only, so a registered sender ID is needed for cross-network service. When outbound is deliberately enabled, the adapter looks up the resulting message ID and rejects any record whose `sms_type` is not `plain`; this check happens after a paid submission and cannot prevent the initial charge or misrouted message.

For IPROG SMS, set `SMS_PROVIDER=iprogsms` and `IPROG_SMS_API_TOKEN=...`. Leave `IPROG_SMS_ENABLE_OUTBOUND=false` for routine use until the controlled pilot passes. The [official API documentation](https://www.iprogsms.com/api/v1/documentation) describes the single-message JSON endpoint, credit lookup, network detection, and message-status lookup. This adapter normalizes a Philippine mobile number to `639...`, sends the token only in JSON bodies, and requires a successful response with a message ID before reporting acceptance. It calls the provider's network detector before a paid send and blocks Smart/TNT unless `IPROG_SMS_ALLOW_SMART_TNT=true`; set that only after an approved custom sender is active. Unknown networks fail closed. IPROG's [network FAQ](https://www.iprogsms.com/faqs) says its shared sender covers Globe/TM/DITO/GOMO but needs an approved custom sender name for Smart/TNT. Confirm handset receipt separately. Network detection can be stale after number portability, so a supported-network result is not a delivery guarantee.

**IPROG pilot, 30 September 2026:** The user-provided token authenticated successfully, and the read-only credit check returned 5.0 credits. The provider's network detector classified both previously supplied test numbers as Smart/TNT. The logged-in account's Sender Names page showed no custom sender name. No paid IPROG SMS was submitted to those numbers. A controlled live send awaits a user-controlled Globe/TM/DITO/GOMO number or an approved Smart/TNT sender. The local configuration keeps outbound disabled.

For TextBee (`textbee.dev`), set `SMS_PROVIDER=textbee`, `TEXTBEE_ENABLE_OUTBOUND=true`, `TEXTBEE_API_KEY=...`, and `TEXTBEE_DEVICE_ID=...` in the ignored `backend/.env.local`. Phone numbers are normalized to E.164 (`+639...`) before posting to `/api/v1/gateway/devices/{deviceId}/send-sms` (or `/api/v1/gateway/send-sms` if `TEXTBEE_DEVICE_ID` is omitted).

**TextBee pilot, 21 October 2026:** Verified active paired gateway device `realme RMX2189` (`6ad7ac1f60b1138230b5c30d`, SIM1 Smart `IN_SERVICE` / `READY`) and dispatched one templated PULSO report notification (`CE-2026-1021`, Brgy. 175, Roads & Bridges), returning `accepted=True`, `smsBatchId='6ad7b1d160b1138230ba6021'`, and `status='sms added to queue for processing'`.

Run the isolated tests from `backend/` with `python -m pytest tests/test_sms_providers.py -q --disable-warnings`. These tests replace the network client and do not send SMS or spend credits.

## One controlled live test

Use a number controlled by the tester. An administrator can invoke the OTP sender once with a fresh six-digit code; the provider result should contain a message ID and status. Do not print or record the code in shell history, server logs, screenshots, or tickets. Check actual handset receipt separately. The resident `/api/auth/phone/send-otp` endpoint requires that the number already belongs to a resident account; it should be used only with a test resident, and the `/verify-otp` endpoint should then be exercised with the received code.

**Controlled live test, 29 September 2026:** One request for a plain PhilSMS message with the exact body `1` was submitted to the first user-provided test number through `dashboard.philsms.com/api/v3/sms/send`. The provider returned message ID `6abb7a91f074e` and status `delivered`; a read-only lookup returned `Delivered` but `sms_type=voice`. The account balance moved from 29 to 28 units. The user reported no SMS receipt.

**Follow-up test, 29 September 2026:** At the user's request, one more request for `1` was submitted to a different test number. PhilSMS returned message ID `6abb7b8acc5f7`, and a separate lookup reported `Delivered` but `sms_type=voice`. The account balance moved from 28 to 27 units. The user reported no SMS receipt on the second handset either. The dashboard's All Messages table independently labels both records `API / Voice / Delivered`. This is a provider-side channel discrepancy, not evidence that the phones received SMS. There is no trustworthy delivery ETA for these records. No repeat was sent to either number.

**Release gate:** Keep PhilSMS outbound disabled. Ask PhilSMS support to investigate the two message IDs and the mismatch between documented `type=plain` requests and Voice records, and register a sender ID that supports the recipient networks. Resume with a single controlled, handset-confirmed test only after the provider clarifies the route and sender requirements. Do not use this route for OTPs, emergency alerts, or resident notifications until that test passes. The two user-authorized paid tests are complete; any further paid test requires a new request.

The announcement module still lacks an approved recipient selection and dispatch worker; its SMS/email channel records remain pending rather than fabricated as delivered. Durable delivery records, resend limits, multi-worker OTP attempt limits, and broader authentication hardening remain necessary before production deployment.
